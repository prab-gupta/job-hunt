## Essay 1 - "Tell us about something you have built using AI. What was it, what did you use, and which parts did you do rather than the agent?"

I built FlowSpace's listing bot: given a workspace provider's name and a brochure in any format, PDF, website, photo, or spreadsheet, it drafts a full listing and sends it to our backend, now used across 900+ listings. Stack: n8n for orchestration, Claude for extraction and drafting, TypeScript for the backend logic and the review step.

What the agent did: parsing unstructured brochures into structured fields, writing first-draft descriptions, matching photos to typed slots, and flagging facilities against our enum.

What I did instead of the agent: decided where the human-in-the-loop checkpoint had to sit, because a wrong price or address on a live listing is worse than a slow one. I wrote the spec for what counts as a good listing, decided which fields could be trusted straight from a source document versus which needed checking against our own live data, and built the escalation path for ambiguous sources, a photo gallery from the wrong building, a stale price sheet. The agent is fast and confident even when it is wrong. My job was deciding what confident output was allowed to ship without a person looking at it first, and building the checks that catch the rest.

## Essay 2 - "Take one technical decision inside that project, a number you chose, a tool you picked, an approach you settled on, and tell us why you did it that way instead of the obvious alternative."

Migrating FlowSpace off its legacy platform, I had to move each entity's data into a coded Next.js and Laravel stack while the product stayed live. The obvious alternative was one blanket approach: export everything to CSV, import it once, cut over. I decided against that and went per-entity instead, mixing API endpoint syncs for anything still changing in the old system, bookings, users, with one-time CSV exports for anything frozen, historical records. The reasoning: a single big-bang CSV cutover assumes nothing changes between export and go-live, and FlowSpace members were booking spaces the whole time we migrated. Anything live-critical needed to keep syncing through an API until the actual cutover moment, not a snapshot taken days earlier. It cost more setup, building and testing each sync path separately instead of one script, but it meant no booking data went stale mid-migration, and we could cut each entity over on its own schedule instead of one all-or-nothing weekend.

## Essay 3 - "Have you set up your own coding-agent harness? If so, describe your actual setup: which tools, how they are configured, and what you changed from the defaults."

Yes. Claude Code is my daily driver, and I route work by cost and risk rather than sending every task to the same model. Search, file location, and small mechanical edits, a rename, a one or two file fix, go to a cheap fast model. Diff reviews and moderate builds go to a mid-tier model. The top-tier model is reserved for architecture decisions, hard debugging, or anything touching production data, payments, or push paths, never for routine work.

I changed two defaults. First, standing rules that used to live in every prompt, no fabricated commit co-authorship, check for an existing library before writing custom code, now live as automatic hooks so they apply without me restating them each session. Second, for anything risky on a live product, I never let an agent edit the live route in place. I work on its own branch, add a forked copy of the route, and keep any shared library change additive-only, so the existing path keeps working while the new one is tested, and I can drop the change cleanly if it does not hold up.

## Essay 4 - "Have you built an agentic pipeline to automate development, for example a planning agent, an architect agent and an implementation agent working in sequence? If you have, describe the whole setup. If you have not, just say so; it is not a requirement."

Yes, in a lighter form than a fully autonomous pipeline. Before any multi-step change I have the agent produce a written plan first, which I review and adjust, then a separate pass executes it, and a separate review pass checks the diff before it ships, so planning and execution are not run in the same breath.

What I have not built is a fully autonomous loop where a planning agent hands straight to an architect agent and an implementation agent with no person in between. I keep a human checkpoint between plan and execution, and again before merge, because the failure mode I have actually seen is an agent executing a good-looking plan that has a wrong assumption baked into it, and I want someone to catch that before code gets written, not after it is already merged.

## Essay 5 - "What is the last thing an AI agent got badly wrong for you, and how did you catch it?"

On a data migration pass for a legacy-platform archive, an agent reported a small null count on one field and presented that as a clean migration, almost nothing missing. I did not take that number at face value and asked it to classify every null as either source-absent, the original data genuinely had nothing there, or a mapper bug. That split showed the small null count was hiding a mapper bug that had silently dropped close to 29 percent of that field's real values: the source data existed, the migration script simply was not reading it into the mapped column. A small, confident null count in a migration report is not proof of a clean migration. I now ask for that source-absent versus mapper-bug split on every field before I trust a migration count, rather than accepting the top-line number.
